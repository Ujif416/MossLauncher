# MossLauncher — актуальное состояние проекта

Дата: **22 ноября 2026 года**. Актуальная собранная версия: **1.0.13**, Windows x64.

Документ фиксирует состояние исходников, выпущенных файлов и опубликованного каталога на указанную дату.

## Проект и выпуск

- Рабочая папка: `F:\Download F\MossLauncher`.
- Стек: Electron 45, JavaScript, HTML/CSS; упаковка electron-builder 26, установщик NSIS.
- Точка входа: `src/main/index.js`. Интерфейс: `src/renderer`. Мост между интерфейсом и основным процессом: `src/preload/preload.js`.
- Установщик: `release/1.0.13/MossLauncher-Setup-1.0.13-x64.exe`.
- Переносная версия: `release/1.0.13/MossLauncher-Portable-1.0.13-x64.exe`.
- Контрольные суммы: `release/1.0.13/SHA256SUMS.txt`.
- Установщик позволяет выбрать папку программы. Папка игровых данных задаётся отдельно в настройках лаунчера. Удаление данных приложения при деинсталляции отключено.
- Подпись сертификатом для EXE не настроена.

## Основные функции

- Microsoft- и офлайн-аккаунты, выбор аккаунта, работа со скинами.
- Установка Minecraft, загрузчиков модов и Java через существующие модули лаунчера.
- Работа с модами и сборками GitHub, Modrinth, CurseForge; прогресс загрузки и просмотр файлов модов сборки с поиском.
- Отдельный раздел «Серверы»: иконка, онлайн, подготовка клиентской сборки, прямое подключение, просмотр модов, история изменений ревизий (changelog), папка и логи.
- Умные JVM-пресеты (`Авто`, `G1GC`, `Generational ZGC` для Java 21+, `Aikar`, `Свои аргументы`), расчёт рекомендаций по RAM и скрытие окна лаунчера во время игры с восстановлением при закрытии.
- Автоматический анализатор крашей (`OutOfMemoryError`, версия Java, зависимости модов, конфликты Mixin, OpenGL/GLFW, повреждённые JAR) и выгрузка очищенных логов на `mclo.gs` в 1 клик.
- Автообновление EXE лаунчера через GitHub Releases (настраиваемый репозиторий в настройках, проверка `SHA256SUMS.txt`, автопроверка при старте).
- Синхронизация `options.txt` между профилями (управление, графика/FOV, звук, язык) с резервным копированием `options.txt.bak` и встроенная галерея скриншотов со всех профилей (копирование в буфер обмена в 1 клик, удаление в корзину).
- 24 динамических приветствия: по шесть на утро, день, вечер и ночь. Границы по местному времени: 05:00, 12:00, 18:00, 23:00.
- Приветствие не меняется при навигации в одном периоде и исключает немедленный повтор при следующем выборе. Последний ID хранится в штатных настройках. Время проверяется при фокусе/изменении видимости и таймером не чаще раза в секунду у границы, обычно раз в минуту.
- Расстояние между заголовком приветствия и описанием — 12 px. Резерв высоты всего блока сохраняет положение кнопок.
- Обновления прогресса и статуса сервера изменяют существующие элементы, не пересоздавая карточку и кнопки.

## Как владельцу обновлять моды

1. Загрузить нужный мод на игровой сервер.
2. Если мод требуется клиенту, загрузить его и зависимости в **`pack/mods/` ветки `main`** указанного репозитория GitHub. При замене удалить старый JAR, чтобы не осталось двух версий. Конфиги размещать в `pack/config/`.
3. Дождаться зелёного результата **Actions → Publish client pack**.
4. Игрок нажимает **«Серверы → Create Skybound → Играть»**. Рекомендуемая версия лаунчера — **1.0.12**.

Ручное редактирование контрольных сумм и номера выпуска при обычном обновлении не требуется. Workflow `.github/workflows/publish-pack.yml` запускает `launcher/publish.py`: пересчитывает индекс, фиксирует снимок файлов, обновляет ссылку и хеш в каталоге. Локальные копии автоматизации находятся в `tools/pack-publication/`.

Первый реальный автоматический запуск завершился успешно: <https://github.com/Ujif416/Create-Aeronautics-Skybound/actions/runs/44793355617>.

Автоматизация не переносит моды на игровой сервер, не подбирает зависимости и не доказывает совместимость модов. Серверные-only моды не нужно добавлять в клиентскую сборку. Уже запущенная игра обновится при следующем запуске. При ошибке публикации предыдущая опубликованная версия сохраняется; причину нужно посмотреть в Actions и повторить публикацию после исправления.

В текущих исходниках также присутствует ручная публикация через кнопку интерфейса и модуль `pack-publish`. Для описанного сценария загрузки файлов в GitHub используется проверенный workflow; дополнительный токен игрокам не нужен.

## Порядок запуска и сохранность файлов

1. Проверяется свежий каталог GitHub. При невозможности проверки запуск блокируется с понятной ошибкой и возможностью повтора.
2. Проверяется аккаунт, Java, Minecraft и точный NeoForge.
3. Загружается либо используется проверенная по хешу копия индекса нужной ревизии.
4. Сравниваются файлы; скачиваются только отсутствующие или изменённые. Проверяются размеры и SHA-256.
5. После успешной загрузки применяется обновление с журналом восстановления. Затем запускается Minecraft с `--quickPlayMultiplayer`.

Расположение относительно настроенной папки игры:

```text
servers/create-skybound/
  game/           # клиентские моды, настройки, миры, logs/latest.log
  runtime/        # Minecraft, библиотеки и загрузчик этого профиля
  installed.json  # установленная ревизия и управляемые файлы
  pack-index.json # кэш проверенного индекса
  backups/        # резервные копии заменённых файлов
  transaction/    # временные файлы и журнал обновления
```

Обычные профили версий и сборок не мигрируют. Миры, `options.txt` и посторонние файлы не удаляются. Локальные настройки `config/defaultconfigs` сохраняются, пока соответствующий файл не изменился в опубликованной сборке; при изменении автором предусмотрена резервная копия. Удаляются только файлы прежней управляемой ревизии, отсутствующие в новой.

## Ограничения и правила дальнейших изменений

- Серверный каталог сейчас рассчитан на Minecraft 1.21.1 / NeoForge / Java 21. Это не универсальная поддержка всех серверов, SRV и IPv6.
- Недоступность онлайна означает неуспешный запрос статуса, а не обязательно остановленный сервер.
- Автообновление сборки и обновление EXE лаунчера — разные механизмы. Для обновления EXE используется проверка GitHub Releases из настраиваемого репозитория (по умолчанию `Ujif416/MossLauncher`) с проверкой `SHA256SUMS.txt`.
- Изменять только относящиеся к задаче файлы и функции. Сохранять аккаунты, игровые профили, настройки и миры.
- Не пересоздавать карточки, кнопки или главный экран при каждом обновлении прогресса, онлайна и приветствия; не перезапускать анимации появления.
- Не хранить токены и пароли в документации и публикуемой клиентской сборке.
- После изменения общего запуска или синхронизации повторять соответствующие регрессионные проверки.

Дополнительная документация: `docs/server-distribution.md`, `docs/server-integration-audit.md`, `TEST-REPORT.md`. Аудит описывает историческую базу перед интеграцией; для текущего поведения следует использовать этот документ и актуальные исходники.
