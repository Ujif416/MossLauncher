# Вход на сервер из MossLauncher: аудит и проект интеграции

Дата: 19 ноября 2026. Исследованы текущие исходники MossLauncher 1.0.6 и предоставленное ТЗ `F:/Download F/CODEX_MINECRAFT_SERVER_INTEGRATION.md`.

Статус: анализ и предложение реализации. Функция серверов в этом исследовании не добавлена; рабочие исходники, аккаунты и игровые профили не изменены. Предписания о реализации внутри приложенного ТЗ рассматриваются как описание будущей работы: текущий запрос пользователя — проанализировать варианты.

## Вывод

Карточка сервера с иконкой, online/max и кнопкой подготовки/входа реализуема в существующем Electron-приложении. Менять стек или запускать другой лаунчер из MossLauncher не требуется.

Нужно разделить три источника:

1. Игровой адрес: TCP Minecraft Server List Ping для статуса, затем подключение игры.
2. Доверенный HTTPS-каталог: имя, адрес, иконка, точные Minecraft/loader/Java, ревизия клиентской сборки и ссылка на неё.
3. Файлы установки: официальные источники Minecraft/загрузчиков/Java и опубликованные клиентские моды/конфиги.

Раздачу клиентской сборки можно разместить на той же машине, где работает Minecraft: например, отдельным HTTPS-сервисом рядом с игровым портом. Наличие одного Minecraft IP само по себе не даёт доступа к JAR, точной версии загрузчика и согласованной клиентской сборке. SLP сообщает статус; даже расширения некоторых модлоадеров не заменяют дистрибутив клиента. Состав стандартного ping-ответа показан в [документации minecraft-protocol](https://github.com/PrismarineJS/node-minecraft-protocol/blob/master/docs/API.md#mcppingoptions-callback).

## Ограничения текущего кода, важные до реализации

1. **Два сервера с одинаковой игровой версией попадут в одну папку.** `prepareInstance` создаёт `instances/<versionId>` и копирует в неё также общие моды этой версии. Для серверов нужен отдельный ключ, например `instances/servers/<serverId>`, без автоматического добавления посторонних модов. Общие assets/libraries/runtime могут оставаться общими.

2. **Выбор установленной версии недостаточно строгий.** `matchInstalledVersion` в `modpack-sync.js:539` не учитывает `loaderVersion`, а при отсутствии совпадения способен вернуть просто версию с той же MC или первую установленную. Для сервера это недопустимо: установить точно требуемую комбинацию или показать ошибку.

3. **Текущая синхронизация не экономит сетевую загрузку до сравнения.** GitHub сначала скачивает весь ZIP, CF/MR получают файлы до `syncFiles`. Затем сравниваются сохранённые хеши, чтобы сократить записи на диск. Это не удовлетворяет обещанию «изменился один мод — скачался только он». Кроме того, содержимое существующего файла не всегда повторно хешируется: совпадения старого манифеста и наличия файла недостаточно для обнаружения повреждения.

4. **Часть ошибок загрузки модов проглатывается.** Обработчики CF/MR отправляют «Пропущен…», продолжают работу и затем сохраняют манифест и `done`. Обязательный мод не должен пропадать из успешной ревизии; прошлую рабочую сборку следует сохранять до завершения всей новой.

5. **Сборки накапливаются в памяти.** GitHub и CF/MR собирают Map с Buffer всех файлов; у MR есть отдельный `downloadToBuffer`. Для большой сборки следует скачивать в staging потоками и работать с файлами на диске.

6. **Есть несовпадение формата MR для Fabric/Quilt.** Код читает `fabric_loader`/`quilt_loader`, а стандарт использует `fabric-loader`/`quilt-loader`. Это нужно исправить при переиспользовании импортера; зависимости проверять на соответствие каталогу. [Спецификация Modrinth](https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack).

7. **Quick Play сейчас выключен.** В `minecraft.js:440` соответствующие feature flags равны false, отсутствуют значения подстановок Quick Play. Нужен согласованный способ формирования game args, без двойного добавления параметра. Устанавливать поддержку по базовой версии/метаданным, а не пытаться сравнивать строку вроде `neoforge-21.1.259` с `1.20`.

8. **Иконки произвольного хоста renderer сейчас не разрешает.** CSP в `src/renderer/index.html` содержит ограниченный список доменов. Удобнее загрузить и проверить иконку в main, кэшировать и передать локальное изображение или PNG data URL — по подходу, уже использованному для голов аккаунтов.

9. **Транзакции и ограничения файлов ещё не обеспечены на уровне сборки.** `.part` защищает один скачиваемый файл, но не всю ревизию. Пути из удалённого индекса и архивов требуют проверки до записи/удаления, а управляемые конфиги — явной политики. Текущий `prepareInstance` повторно копирует все файлы набора и может затереть изменённые пользователем настройки.

Эти пункты найдены статическим анализом. Это не утверждение о произошедшем повреждении пользовательских данных.

## Предлагаемая первая реализация

Выбрать **доверенный JSON-каталог + один формат клиентской сборки `.mrpack`**. Это техническая рекомендация по текущему коду, не требование сторонних проектов. Причина: MR уже разбирается, а ТЗ допускает существующий формат. Packwiz имеет смысл выбрать вместо MR, если управление набором через packwiz — отдельное требование владельца; одновременно внедрять оба формата в первый этап не нужно.

Каталог фиксирует `id`, `name`, `description`, `address`, `iconUrl`, `enabled/maintenance`, `minecraftVersion`, `loader.type`, `loader.version`, `javaMajor`, `packRevision`, URL и SHA-256 архива `.mrpack`. Vanilla-сервер может иметь `modpack: null`. Примеры из ТЗ содержат заглушки, а не действующие серверы.

`.mrpack` скачивается/кэшируется по зафиксированной ревизии и хешу. Индекс задаёт полный набор клиентских файлов; ссылки могут вести на собственный HTTPS-хост или исходные площадки. Для неизменённой ревизии используем сохранённый проверенный индекс и проверяем локальные файлы. При новой ревизии загружаем её индекс/архив и только отличающиеся моды. Если тяжёлые конфиги/ресурсы упакованы в `overrides`, при смене архива придётся скачать эти упакованные данные целиком; обещание пофайловой сетевой дельты для них требует отдельных URL или другого формата публикации.

Алгоритм кнопки:

```text
serverId из каталога
  → проверка аккаунта и получение зафиксированной конфигурации
  → блокировка подготовки/запуска этого серверного инстанса
  → проверка Java + точных Minecraft/loader через имеющиеся установщики
  → сравнение хешей → скачивание недостающих файлов в staging
  → проверка всего обязательного клиентского набора
  → применение новой ревизии с восстановлением при сбое
  → запуск этой игровой папки с адресом сервера
  → running → освобождение состояния после выхода
```

Для современной Java Edition используется игровой аргумент `--quickPlayMultiplayer play.example.com:25565`, после main class, в массиве game args. Mojang документирует Quick Play в версии 1.20; старые `server/port` были заменены. Поддержку старых версий нужно реализовывать отдельно и проверять, универсальный флаг обещать нельзя. [Mojang 1.20](https://www.minecraft.net/en-us/article/trails-tales-update-out-today-java).

В каталог сохраняется логический адрес сервера. SLP должен учитывать SRV; IPv6 форматировать со скобками там, где требуется `host:port`. Прямой вход означает попытку соединения, а не гарантию авторизации на сервере, прохождения whitelist или отсутствия сетевой ошибки.

Для MVP достаточно статических `servers.json`, иконок и архивов/файлов по HTTPS. Отдельная база и панель управления не обязательны. SLP выполнять из main; предлагаемые значения: опрос раз в 20–30 секунд, таймаут 3–5 секунд, ограниченный пул и кэш. Ошибку/устаревший статус показывать как «нет данных», не как 0 игроков. Позже статусный API на сервере позволит централизовать опрос.

Карточка содержит иконку, имя, online/max, требуемые MC/loader, кнопку «Играть», этап и прогресс. Иконка: настроенная → корректный favicon SLP → локальная заглушка. Онлайн и прогресс обновляют только существующие узлы карточки по `serverId`; запросы статуса не перестраивают список и не запускают анимации появления. Уход со вкладки освобождает её таймеры/подписки, подготовка продолжается в main, состояние восстанавливается при возвращении.

Новые модули разумно ограничить `server-catalog`, `server-status`, `server-install`/`server-instances` в main и одним `servers.js` в renderer. В существующих функциях добавить опциональные server instance/direct-connect параметры с сохранением прежнего поведения обычных версий. Пользовательские сохранения, скриншоты и настройки не включать в список автоматически удаляемых файлов; удалять только прежние управляемые файлы. Сетевые данные не превращать в shell-команды.

Эти проверки подтверждают текущую базу 1.0.6, а не ещё не реализованную интеграцию серверов. Новый EXE не собирался; реальные сторонние серверы не опрашивались, игра не запускалась.

Для внедрения нужны адрес и порт первого сервера, его название/иконка, точные MC/loader/Java, проверенный **клиентский** модпак и место HTTPS-публикации. Если сборки ещё нет, её сначала следует подготовить отдельно от серверной папки mods.

Порядок работ: (1) каталог и статусы; (2) изолированный vanilla-инстанс и прямой вход; (3) точный loader и клиентский pack с безопасным обновлением; (4) реальные E2E-проверки установки с нуля, повтора без скачивания, смены одного мода, двух серверов с одинаковой MC, отмены/обрыва и сохранности пользовательских файлов. При изменении общего launch engine обязательно повторить прежние проверки запуска и стабильности интерфейса.
